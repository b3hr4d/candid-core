Every Candid type has exactly one TypeScript rendering in this project, and every rendering has a matching runtime schema — an inert data object built from the c combinators that validation, the binary codec, typed actors and form metadata all walk. This page is the complete table of both, plus the handful of shapes that refuse to generate rather than lose information.

Two independent implementations apply this mapping and must agree. The Rust generator candid-core-ts emits a TypeScript module ahead of time; the npm runtime's schemaFromContract builds the same schemas at load time from a canonical Contract JSON document. A Contract is candid-core's validated model of a .did file: a flat array of type nodes addressed by index, a list of named declarations pointing into it, and an optional actor. Both sides read that graph, so the rows below describe both — see The code generator and Schemas from a Contract document for the two entry points.

The Rust crate is 0.1.0-beta.3 and the Contract format is not a stable v1. The mapping below is where the reviewed decisions live — the generator's golden files pin it byte-for-byte — but a pre-1.0 release may still change it.

How to read the tables

  • Contract node is the node kind as it appears in the Contract JSON document. There are eight kinds and no more: primitive, opt, vec, record, variant, func, service, class. There is no blob node, no tuple node and no result node — those are Candid conveniences the graph never encodes, and recognising them is what several rows below do.
  • TypeScript type is the right-hand side of the emitted export type X = … alias.
  • Builder is the expression emitted for export const X: Schema<X> = c.rec(() => …). Every declaration is wrapped in c.rec: declarations are emitted in canonical name order rather than dependency order, and the lazy thunk is what makes a forward reference safe at module initialisation.
  • Schema<in out T> is invariant, so annotating each builder with the alias just emitted makes tsc prove the two are the same type in both directions. That type-check is the equality gate, not a convention.

The eighteen primitives

All eighteen are present in the Contract as {"kind":"primitive","primitive":"<name>"} with the name in snake_case. The width split is the point: nat, int, nat64 and int64 are bigint because a JavaScript number silently corrupts integers past 2^53, while every width that fits a double exactly stays a number.

The actor surface

When the Contract has an actor — the service : { … } at the bottom of a .did — the module emits two more exports: export const actor: Schema<PrincipalValue>, the service schema, and export type Actor, one async method per service method. Parameters are positional and named arg0, arg1, …; the reply convention is zero results ⇒ Promise<void>, one ⇒ Promise<T>, several ⇒ Promise<[A, B]>. createActor<Actor>(actor, canisterId, transport) turns that pair into a live typed client — see Typed actors.

Field names are an input

A Contract stores only the authoritative numeric Candid label id, never the spelling: the id is either written literally (5 : nat) or derived as h = 0; for each UTF-8 byte b: h = (h * 223 + b) mod 2^32. The generator therefore takes names as caller-supplied data through TsNames. With no table, every record field and variant arm renders by the ecosystem's _N_ convention — underscore, the decimal id, underscore — so record { id : nat32 } becomes { _23515_: number }. Service method names are the exception: they are kept in the graph, because you cannot invoke a method by hash.

A whole file, before and after

These are the generator's checked-in fixtures and goldens. The first golden is the whole file; the two after it drop the generated header and import lines to keep the comparison short. Note that output is sorted by declaration name, not source order. 

type Unit = record {};
type Pair = record { nat; text };
type Item = record { id : nat32; label : text; payload : blob };
type MaybeItem = opt Item;
type Note = opt text;
type Items = vec Item;
type Grid = vec vec nat8;

// Generated by candid-core-ts from a candid-core Contract. Do not edit.
import { c, type Schema } from "@candid-core/schema";

export type Grid = Array;
export const Grid: Schema = c.rec(() => c.vec(c.blob()));

export type Item = { id: number; label: string; payload: Uint8Array };
export const Item: Schema = c.rec(() => c.record({ id: c.nat32, label: c.text, payload: c.blob() }));

export type Items = Array;
export const Items: Schema = c.rec(() => c.vec(Item));

export type MaybeItem = Item | null;
export const MaybeItem: Schema = c.rec(() => c.opt(Item));

export type Note = string | null;
export const Note: Schema = c.rec(() => c.opt(c.text));

export type Pair = [bigint, string];
export const Pair: Schema = c.rec(() => c.tuple([c.nat, c.text]));

export type Unit = Record;
export const Unit: Schema = c.rec(() => c.unit());

Six rules in one file: blob and the inner vec nat8 of Grid become Uint8Array; the tuple-syntax record becomes a TypeScript tuple; opt becomes | null; Items references the declared Item by name rather than re-expanding it; the empty record becomes Record<string, never>.

Variants, including a self-referential one:

type Status = variant { ok; busy : nat32; failed : text };
type Numbered = variant { 0 : null; 5 : nat };
type Tree = variant { leaf : nat; node : record { left : Tree; right : Tree } };

export type Numbered = { tag: "_0_" } | { tag: "_5_"; value: bigint };
export const Numbered: Schema = c.rec(() => c.variant({ _0_: c.null, _5_: c.nat }));

export type Status = { tag: "ok" } | { tag: "busy"; value: number } | { tag: "failed"; value: string };
export const Status: Schema = c.rec(() => c.variant({ ok: c.null, busy: c.nat32, failed: c.text }));

export type Tree = { tag: "leaf"; value: bigint } | { tag: "node"; value: { left: Tree; right: Tree } };
export const Tree: Schema = c.rec(() => c.variant({ leaf: c.nat, node: c.record({ left: Tree, right: Tree }) }));

ok has a null payload, so its arm is the bare { tag: "ok" }. Numbered shows the _N_ convention for explicitly numeric Candid labels, which carry no name at all. Tree is self-referential in both the alias and the builder, which is safe because c.rec defers the thunk.

The cases that fail closed

T | null is the honest reading of opt T only when T itself can never be null in TypeScript. Three inner shapes break that, and rather than collapse Candid's None into Some(None), generation refuses. The check is on the inner node, not its spelling, so an opt reached through a declared alias collapses just as surely and is refused just the same.

SourceinnerWhy T | null cannot carry it
type DoubleOpt = opt opt nat;"opt"The classic None versus Some(None): both would be null.
type OptNull = opt null;"null"The payload's only value is already null.
type OptReserved = opt reserved;"reserved"unknown absorbs null entirely.
type Inner = opt nat; then type Outer = opt Inner;"opt"Same as the first row — the alias changes the spelling, not the node.

All four are valid Candid and compile to a Contract without complaint. It is generation that stops.

What the caller observes

In Rust, generate_module returns Err(TsGenError::UnrepresentableOption { declaration, inner }). No error path emits placeholder TypeScript, so you get either a module that compiles or an error naming what could not be represented. Its Display text is exactly: 

declaration `DoubleOpt` wraps `opt` in `opt`: `T | null` cannot distinguish `None` from `Some(None)` there, so generation refuses rather than collapsing the two

In TypeScript, schemaFromContract refuses the same document with a ContractIssue whose code is "unrepresentable_option", at the path of the offending node's inner edge, with the message opt wraps `opt`: `T | null` cannot distinguish None from Some(None) there. See Diagnostics reference for the full code list.

A variant arm whose payload is a declared opt of an uninhabited type — a declared opt empty, or opt of an empty variant — is also refused, with TsGenError::AmbiguousVariantArm. Through a reference its static type is identical to an alias of null, which the type-level classifier must read as a bare tag, while the emitter and the runtime classify it as carrying a value; no type-level rule satisfies both. The anonymous form still works: variant { a : opt empty } renders { tag: "a"; value: never | null } with builder c.opt(c.empty).

Three more refusals, on names rather than shapes

Generation also stops on a name it cannot emit safely. These are the remaining TsGenError variants a well-formed Contract can reach:

InvalidDeclarationName
A declaration name that is not a valid TypeScript type identifier.
ReservedDeclarationName
A declaration named after a binding the generated module itself references — the imports (c, Schema, PrincipalValue), the ambient types its lowerings emit (Array, Record, Uint8Array, Promise), or the actor surface's own names (actor, Actor). All nine are refused unconditionally, so adding a field to a contract cannot start breaking a declaration name that worked before.
ReservedFieldName
A supplied field or arm name shaped like the _N_ id rendering. Erased to a schema key it is indistinguishable from the rendering of numeric label id N, and the codec derives wire ids from keys, so such a name would send id N instead of the name's hash. The runtime's Contract loader refuses the same shape in a name table.

Divergence from agent-js shapes

These types describe the domain, not the transport. That is a deliberate decision recorded on the project's issue tracker: compatibility with the value shapes the agent-js runtime produces is an explicit non-goal. If you are moving code from bindings generated by @icp-sdk/bindgen, the following is what changes at every touch point.

The same CandidWire-shaped bindingcandid-core-tsWhat your code stops doing
record { memo : opt text } { memo: [] | [string] } { memo: string | null } No array unwrapping. value.memo[0] becomes value.memo, and the empty array becomes null. The property is always present either way.
variant { ok : nat; err : text } a single-key object, one key per arm { tag: "ok"; value: bigint } | { tag: "err"; value: string } No probing for which key exists. switch (value.tag) narrows the union, and TypeScript checks exhaustiveness for you.
record { payload : blob } a byte sequence, spelled per generator { payload: Uint8Array } Nothing is accepted but a real Uint8Array. If your existing values are plain arrays of numbers, wrap them once at the boundary.

The two shapes in the middle column that this repository states it verified against @icp-sdk/bindgen 0.4.0 are the [] | [T] optional and the single-key variant object. The blob row states only what candid-core-ts commits to; check your own generator's output for its byte-vector spelling.

Feeding these types to a classic agent needs a boundary conversion, and this project does not supply one — it is recorded as future work. The supported path instead is the generated actor schema plus createActor over a two-method byte-pipe transport, where the package's own codec does all the encoding and never hands a schema to an agent. In a value's lifetime the domain shape is what your application code sees, and the wire shape never appears at all. 

import { createActor } from "@candid-core/schema/actor";
import { actor, type Actor, type TransferArg } from "./ledger.ts";

const ledger = createActor(actor, "ryjl3-tyaaa-aaaaa-aaaba-cai", transport);

const arg: TransferArg = {
  to: { owner: recipient, subaccount: null },   // Account; opt blob absent
  fee: null,                                    // opt Tokens, absent
  memo: null,                                   // opt blob, absent
  from_subaccount: null,
  created_at_time: null,
  amount: { e8s: 100_000_000n },
};

const result = await ledger.transfer(arg);
if (result.tag === "ok") {
  console.log("block index", result.value);
}

The type names in that snippet come from the generator's ledger golden, whose fixture (crates/candid-core-ts/tests/fixtures/ledger.did) is byte-identical to the ledger interface in the repository's benchmark corpus, benches/corpus/ledger.did.

A canister method takes an argument of a declared Candid type, and sooner or later somebody has to type that argument into a screen. The type already says everything a form needs to know: which fields exist, in what order, what each one accepts, which are optional, which choices a variant offers. The ./forms subpath of @candid-core/schema turns a schema into that description, as data.

Form metadata is a UI-agnostic description of a schema that a renderer can walk. It names a control per node — text, checkbox, bigint, choice — with the constraints and labels that go with it, and a $-rooted path identifying where the node sits. It contains no components, no DOM, and no reference to any framework. Bindings consume the model; they are not part of it. 

import { c } from "@candid-core/schema";
import { formModel, formNodeAt, type FormNode } from "@candid-core/schema/forms";

The two functions

formModel ./forms 
export function formModel(schema: AnyFieldSchema): FormNode

Build the model for a schema. The root's path is $. A foreign object, or a schema kind this walk has no control for, is a programmer error and throws TypeError. A rec is not followed here — it becomes a lazy node — so a chain that never terminates throws only where something expands it: formNodeAt, your own loop, or the arm resolution a variant does eagerly to classify tag-only arms.

formNodeAt ./forms 
export function formNodeAt(root: FormNode, path: string): FormNode | undefined

The node a path addresses, expanding lazy nodes along the way. undefined when the path addresses nothing this model describes — an unknown key, a malformed path. The paths it accepts are exactly the validator's, which is the point of the function.

What a node carries

A FormNode is FormCommon & FormControl: where it sits, plus how to edit what is there. 

export interface FormCommon {
  /** `$`-rooted path in `validate`'s grammar. */
  readonly path: string;
  /** The rendered label (field key or arm tag); absent at the root. */
  readonly label?: string;
  /** The numeric Candid id when `label` is the `_id_` rendering. */
  readonly numericId?: number;
}

export type FormNode = FormCommon & FormControl;

path is the address, and it is what makes the model useful beyond drawing: it is a stable key for the value you are editing, for a per-field error, and for focus management. label is the rendered field key or arm tag — the name table the schema was built with has already been applied, so it is the name a user should see. numericId appears only when the Candid field had no source name and the key is the _N_ rendering of its numeric label id; a UI can then present unnamed fields however it likes instead of showing _5_.

An arm of a choice is its own small record:

export interface FormArm {
  readonly tag: string;
  readonly numericId?: number;
  /** A tag-only arm (`null` payload) needs no payload editor. */
  readonly tagOnly: boolean;
  /** The payload editor for `{ tag, value }` arms; undefined when tagOnly. */
  payload(): FormNode | undefined;
}

tagOnly is the distinction a variant UI has to get right. An arm with a null payload is a bare { tag } value, so selecting it must not produce a value key at all — the validator rejects one. Every other arm needs its editor, and payload() builds it on demand at the path <parent>.value.

A worked example

const Account = c.record({
  owner: c.principal,
  subaccount: c.opt(c.blob()),
});

const model = formModel(Account);
if (model.control !== "group") throw new Error("expected a group");

model.fieldLabels;      // ["owner", "subaccount"]
model.fields[0]();      // { path: "$.owner", label: "owner", control: "principal" }

const subaccount = model.fields[1]();
// { path: "$.subaccount", label: "subaccount", control: "optional", inner: ƒ }
if (subaccount.control === "optional") {
  subaccount.inner();   // { path: "$.subaccount", control: "bytes" }
}

Three details are worth pausing on. The children are thunks: fields holds functions, not nodes, so nothing below the level you asked for is built. The optional node and its inner node share the path $.subaccount, because the presence toggle and the value edit the same place — opt T is T | null with the property present, so switching the toggle off writes null rather than deleting the key. And the inner node has no label: the label belongs to the field, and repeating it would make a renderer draw it twice.

Because thunks and bigint bounds are not JSON values, the model is not something you can hand to JSON.stringify directly. A small projection is all it takes when you want the shape on paper: 

function outline(node: FormNode): Record {
  const base = { path: node.path, label: node.label, control: node.control };
  if (node.control === "group") return { ...base, fields: node.fields.map((f) => outline(f())) };
  if (node.control === "optional") return { ...base, inner: outline(node.inner()) };
  return base;
}

Numeric bounds ride along on the nodes that have them. A nat64 field gives you the exact range, as bigints: 

const Tokens = c.record({ e8s: c.nat64 });
const tokens = formModel(Tokens);

Driving a renderer

A renderer is a recursion over the model, guided by the value being edited. The model decides what to draw; the value decides how far — how many list rows, which arm of a choice, whether an optional is switched on. The helpers below (heading, toggle, select, input) are yours; nothing in the package supplies them. 

function unwrap(node: FormNode): FormNode {
  let current = node;
  while (current.control === "lazy") current = current.expand();
  return current;
}

function render(parent: HTMLElement, node: FormNode, value: unknown): void {
  const current = unwrap(node);

  switch (current.control) {
    case "group": {
      const record = (value ?? {}) as Record;
      for (let i = 0; i < current.fieldLabels.length; i += 1) {
        const label = current.fieldLabels[i];
        parent.append(heading(label));
        render(parent, current.fields[i](), record[label]);
      }
      return;
    }
    case "list": {
      const rows = Array.isArray(value) ? value : [];
      for (let i = 0; i < rows.length; i += 1) render(parent, current.item(i), rows[i]);
      return;
    }
    case "optional": {
      parent.append(toggle(current.path, value !== null));
      if (value !== null) render(parent, current.inner(), value);
      return;
    }
    case "choice": {
      const tag = (value as { tag?: string } | null)?.tag;
      parent.append(select(current.path, current.arms.map((arm) => arm.tag), tag));
      const payload = current.arms.find((arm) => arm.tag === tag)?.payload();
      if (payload) render(parent, payload, (value as { value?: unknown }).value);
      return;
    }
    default:
      parent.append(input(current.path, current.control, current));
  }
}

Every branch keys its widget on current.path, which is what makes the next section work. The default arm covers the leaf controls: your input helper reads control to pick an element and reads min, max or bits off the same node when they are there.

Recursion is lazy, deliberately

Every generated declaration is wrapped in c.rec, so formModel(Account) on a generated Account returns a lazy node, not the group the record describes. Schemas built from a Contract document at runtime are lazy at every edge. Expand in a loop, not with a single expand() — chains of two or more hops are ordinary, because a declaration's body can be another declaration.

The laziness is load-bearing rather than an artefact. Consider type List = opt record { head : nat; tail : List }. Its fully expanded form model is infinite, so the model cannot be built eagerly and expansion has to be the caller's move. Driving the recursion from the value, as the renderer above does, is what terminates it: you expand one tail for each element the user has actually added.

formNodeAt is the one function that expands on your behalf, because a path names a node that is reachable by definition. Its unwrapping is bounded: a rec chain that runs past 256 hops throws TypeError rather than hanging.

Issue paths address form nodes

Node paths use exactly the grammar validation issues use, and that is not a coincidence — it is the reason both modules render paths the same way. So a validation failure resolves to the control the user typed into, with no bookkeeping of your own: 

import { validate } from "@candid-core/schema/validate";

const result = validate(Tokens, { e8s: -1n });
if (!result.ok) {
  for (const issue of result.issues) {
    const node = formNodeAt(formModel(Tokens), issue.path);
    // issue.path is "$.e8s"; node.control is "bigint", node.label is "e8s"
    showError(node?.path ?? issue.path, issue.message);
  }
}

Record, tuple, list, optional and func-reference paths resolve directly. A variant is the one case with a caveat: the model does not know which arm the user picked, so .tag and .value resolve to the choice node re-pathed to match the issue (or, for .value, straight to the payload editor when exactly one arm has one), and a deeper segment resolves through the arms only when exactly one arm's shape describes it. When more than one arm could match, you get undefined — an honest answer rather than a guess. Quoted keys travel the same grammar, so an issue at $["has space"] addresses its node too.

What this module does not do

  • It does not render. There are no components, no DOM calls, no CSS, and no opinion about layout. It emits a description; you draw it.
  • It does not validate. min, max and bits are hints for choosing and configuring a widget. They mirror what validate enforces, but the form model enforces nothing — run validate before you submit, and treat its issues as the authority.
  • It knows nothing about any UI framework. No React, no Vue, no Svelte, no signals, no store. The whole subpath imports two things: the schema core and the label helpers.
  • It does not hold your value. The model describes the type, not the data. State management, dirty tracking and submission are entirely yours; the model's contribution is that every node hands you a stable path to key that state on.

Nothing here requires generated code. Load a canonical Contract document with ./contract, hand the resulting schema to formModel, and you have a form for an interface the application never compiled against. The nodes will be lazy at every edge — expand in a loop, as above.
